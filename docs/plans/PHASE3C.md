## 4. PROPOSED first milestone

Objective: make the intended local-session boundary executable and independently reviewable through a versioned contract, finite synthetic transcript vectors and offline conformance checks.

Engineering value: reviewers can see exactly which administrative/session behaviors are required, rejected or deferred before a stateful engine, durable sequence store or transport makes those choices expensive. There is no new public UI or operational endpoint in this milestone.

### Included, subject to the decisions in section 10

- A versioned session-profile document that distinguishes base FIX requirements, bilateral lab restrictions and future implementation choices.
- Explicit synthetic session identity, directional sequence vocabulary, message classes, transcript preconditions, expected classifications and bounded inputs. No reuse of financial keys as transport identities.
- A finite, independently authored manifest of raw SOH examples and ordered transcripts, including supported cases and deliberate invalid/unsupported cases.
- Offline contract/fixture validation in TypeScript tests and an independent Python reference checker. The checker evaluates approved transcript rules; it is verification tooling, not a running session engine.
- An additive invocation from the existing FIX verification command, preserving its original Python tests and all 14 encoded frames.
- A specification of the future handoff boundary: only complete, authorized application evidence could reach the existing SDK in a later approved milestone. Administrative traffic cannot call APPLY, consume financial capacity or claim delivery.

### Excluded

No socket, TCP listener, initiator/acceptor process, timer-driven heartbeat service, automatic reconnect, replay daemon, durable session store, QuickFIX engine installation, genuine peer interoperability claim or session-to-financial wiring. No hosted database, public activation, new HTTP/API/UI, production enablement, external counterparty, real market/trading connection or Phase 4 feature. No migration, role/grant, financial writer, SQL verifier/pin, capacity policy, deadline/retry, dependency or workflow change is proposed.

### Measurable completion criteria

1. Owner resolves every implementation-blocking decision below; the approved contract has no ambiguous executable rule or assumed delivery guarantee.
2. Every approved rule has a named positive, negative or explicitly unsupported vector, with exact expected classification and immutable byte identity. Every vector is discovered and executed by the intended checks; no silent omission or unknown status is accepted.
3. Independent Python validation rejects controlled framing/header/field/sequence/transcript corruption without importing TypeScript or deriving expected results from its output.
4. Existing four-message behavior, goldens, financial sources, SQL/pins, migrations 001–008, privileges and execution workloads are byte-preserved; required legacy and database gates retain their cases.
5. The evidence identifies exact source/tree, fixture hashes, independent oracle provenance, actual discovered/executed totals and first failures. Zero skipped mandatory cases or accepted flaky passes; no timeout/retry expansion.
6. Review explicitly states **offline conformance only**. Completing 3C0 is not completion of all Phase 3C or authorization for sessions, sockets, interoperability, publication or deployment.

## 6. Contract, schema, compatibility and security implications

- Keep the application codec's D/8/F/9 profile unchanged. An administrative example valid for the proposed session contract must not be silently accepted by the existing application decoder or treated as financial ingress.
- Session sequence, B2 protocol command sequence, logical message/work UUID, original application request key, immutable prepared financial key, capability generation and lane fence remain distinct concepts. Missing mappings are unresolved; syntactic CompIDs are not authentication.
- Do not reinterpret `fix_channels.epoch=1`, existing sequence slots, BIND history or prepared keys as a session database. New durable state would require a separately approved additive migration, compatibility, ownership, retention and independent-verifier design; never edit migrations 001–008 or add an unreviewed ninth migration here.
- No schema revision, source-pin, RLS policy, private-helper permission, application grant or role change. No database credential or capability is needed for the offline tool.
- Preserve numeric-string watermark contracts, RECORD/INGEST_REJECTED semantics, source-tampering failure, one-snapshot financial coverage and false delivery/external-completeness fields. Do not add a fallback verifier.
- Preserve 512/1,024 ceilings, four retained bindings, 25-command/43-event reservations, effect-backed consumption and finite two-slot rotation headroom without RELEASE replenishment. Preserve 15-second lanes, statement/transaction bounds and existing bounded application recovery behavior.
- Keep new verification inputs finite; recommended ceiling is no larger than the existing 8 KiB frame/64-field/256-byte-value bounds unless the owner approves an explicit separate session-profile bound. Keep the existing stream's 16 KiB buffer and batch bounds unchanged.
- Use public synthetic fixtures only. Errors use bounded codes/case IDs rather than raw input, bearer headers, capabilities or full database URLs. No new trust follows from dictionary conformance.

Do not describe the June PDF as the latest edition or claim complete current-standard conformance.
- Every fixed identity, finite bound, supported subset, diagnostic, closed-world transcript assumption and strict restriction below is a **new bilateral lab proposal**. References to session concepts do not imply implementation of mandatory full-engine behavior outside this subset.

### 17.2 Corpus and interfaces

Use only the section 5 file set. The existing application decoder must continue rejecting administrative messages; do not widen it to reuse its business-message entry point.

Proposed manifest root: strict object with exactly `version="tradeflow-fix-session-corpus-v1"` and `cases`. Each case has exactly `id`, `events`, `expected`. Case IDs match `C[0-9]{2}_[A-Z0-9_]{1,48}` and are globally unique.

Events are a nonempty ordered array. An event is exactly one of:

- Frame: `{kind:"FRAME",direction:"I_TO_A"|"A_TO_I",file:string,sha256:string}`.
- Connection observation: `{kind:"CONNECTION_LOST"}` or `{kind:"RECONNECT_ATTEMPT"}`; it has no invented wire frame.
- Last event: exactly `{kind:"END"}`, once at the end of every case.

A frame filename is one flat relative `[a-z0-9_-]{1,64}.fix` name within the manifest's own directory (the canonical default is `test-data/fix44/session/`); no separators, drive prefixes, absolute paths, dots beyond the final suffix, symlinks or reparse points. Files are raw byte inputs and must never be normalized. Conformant fixtures contain actual SOH without BOM/newline; deliberate invalid fixtures may violate framing and must reach FRAME_INVALID after admission. Hash raw bytes before parsing. Inventory every *.fix in that directory, require every file referenced, and reject unexpected/missing files, unknown keys, duplicate JSON keys, duplicate IDs and invalid expected enums. Reusing a fixture across cases is allowed only with the identical declared hash.

Limits, checked before unbounded allocation: manifest at most 128 KiB; at most 64 cases; at most 32 FRAME/connection events plus final END per case; at most 256 KiB of unique raw fixture bytes; frame at most 8 KiB, 64 fields, 256 bytes/value. Manifest/case/event/unique-byte and raw-file-size admission failures exit 2 before evaluation; bounded per-frame field/value-count violations yield INVALID/FRAME_INVALID during step 2. The file scanner must reject oversized raw files before loading them. These are proposed offline limits, not amendments to the existing stream's 16 KiB/16-message limits.

`expected` has exactly `classification`, `code`, `event_index`, `state`, `next_i_to_a`, `next_a_to_i`, `pending_i`, `pending_a`. Indices are zero-based; counters and pending IDs describe the **last accepted prefix** before a terminal failure/out-of-scope event. For a normal END they describe the final accepted prefix. Pending entries are an allowed TestReqID or null.

The proposed Python API is `evaluate_case(case, frames_by_name) -> dict` in `verification/python/fix_session_reference.py`; the returned dict has the same eight result fields plus the five fixed claim-limit booleans above. `verify_corpus(manifest_path) -> list[dict]` validates complete discovery/hashes, evaluates cases, compares literal expectations and returns reports in manifest order. Import has no side effects. CLI takes one optional manifest path, defaulting to the canonical corpus path; it prints bounded case-ID/code summaries only.

CLI exit 0 means **all declared positive, negative, incomplete and out-of-scope cases matched their independently reviewed expectations**. It never means every transcript is conformant. Exit 1 means an expectation mismatch; exit 2 means corpus/schema/hash/resource or unexpected checker failure. Missing/unknown cases and errors cannot become an empty successful run. No raw message, unexpected exception text, path credential or secret is printed. No evidence-output file is required for 3C0.

TypeScript's tests inspect the YAML/manifest and literal raw-byte/case expectations and characterize the unchanged application-decoder boundary. They do not run a second session state machine or derive expected verdicts from Python. Python may reuse the existing immutable dictionary/framing helper, but not its four-message bilateral application profile or production code. Contract YAML documents rules; it must not supply the expected transition algorithm to both the implementation and its oracle.

### 17.4 States and transitions

Fresh case state is `NEW`; directional counters `next_i_to_a=next_a_to_i=1`; pending_i/pending_a=null. Counters refer to observed new messages in each direction. They are distinct from B2 lane, message, attempt, economic key, generation or fence identities.

For a supported, fresh, valid, in-sequence FRAME, perform the following transition atomically, then increment only its directional counter. Any rejected event leaves the last accepted prefix unchanged.

| State            | Accepted next event                                                 | New state / effect                                           |
| ---------------- | ------------------------------------------------------------------- | ------------------------------------------------------------ |
| NEW              | I_TO_A Logon                                                        | LOGON_PENDING                                                |
| LOGON_PENDING    | A_TO_I Logon                                                        | ESTABLISHED                                                  |
| ESTABLISHED      | Heartbeat without 112 in either direction                           | Same state; no pending request cleared                       |
| ESTABLISHED      | TestRequest by I or A with no pending request for that requester    | Set pending_requester to 112; same state                     |
| ESTABLISHED      | Opposite-direction Heartbeat with the requester's exact pending 112 | Clear that pending entry only; same state                    |
| ESTABLISHED      | Logout in either direction with both pending entries null           | LOGOUT_PENDING_I or LOGOUT_PENDING_A, identifying the sender |
| LOGOUT_PENDING_I | A_TO_I Logout                                                       | CLOSED                                                       |
| LOGOUT_PENDING_A | I_TO_A Logout                                                       | CLOSED                                                       |
| CLOSED           | END                                                                 | IN_SCOPE_CONFORMANT/COMPLETE                                 |

Otherwise reusing an earlier TestReqID, even after response, is INVALID/TEST_REQ_ID_REUSED. Crossed requests, one outstanding per requester, are supported and must be answered independently. Logout with an outstanding request is OUT_OF_SCOPE/ERROR_LOGOUT_UNSUPPORTED; this deliberately does not model error-driven logout.

Any other **fresh in-sequence** supported frame in NEW, LOGON_PENDING or a LOGOUT_PENDING state is INVALID/STATE_TRANSITION. In ESTABLISHED a new Logon is INVALID/STATE_TRANSITION. For CLOSED specifically, classify a new Logon as OUT_OF_SCOPE/RECONNECT_UNSUPPORTED and another supported frame as INVALID/AFTER_CLOSED before fresh sequence comparison, as ordered below. Simultaneous logout is not modeled: the declared ordered observations assign first/response by event order; independent send/arrival concurrency is NOT_EVALUATED.

END before CLOSED yields INCOMPLETE: in NEW use EMPTY_SESSION; LOGON_PENDING use LOGON_REPLY_MISSING; ESTABLISHED with a pending request use TEST_RESPONSE_MISSING, otherwise LOGOUT_MISSING; either LOGOUT_PENDING state uses LOGOUT_REPLY_MISSING. No timeout is inferred. CONNECTION_LOST terminates INCOMPLETE/CONNECTION_LOST unless already CLOSED (INVALID/AFTER_CLOSED). RECONNECT_ATTEMPT terminates OUT_OF_SCOPE/RECONNECT_UNSUPPORTED in any state, without counter reset.

### 17.5 Sequence and diagnostic precedence

No buffering, sequence repair, reset or replay is implemented.

1. Validate whole-corpus schema, discovery, hashes and bounds first; a corpus failure exits 2 rather than inventing case reports.
2. Process a case in declared event order. At each FRAME check bounded framing, mandatory common header, timestamp/replay-field structure and direction identity. Malformed framing/header is INVALID/FRAME_INVALID; direction/49/56 mismatch is INVALID/COMP_ID_MISMATCH.
3. Classify excluded known headers; then dispatch message type and validate supported-body schema from 17.3. Schema errors precede exclusion of body options. Explicit Logon 141=Y is OUT_OF_SCOPE/RESET_UNSUPPORTED after required field/primitive validation, before other valid excluded body options. Known nondefault options use PROFILE_OPTION_UNSUPPORTED.
4. Any supported message with structurally valid 43=Y terminates OUT_OF_SCOPE/REPLAY_UNSUPPORTED. It is not accepted as fresh, even when tag 34 equals the expected number.
5. For a remaining supported frame when the state is CLOSED, Logon is RECONNECT_UNSUPPORTED and any other supported message is AFTER_CLOSED, regardless of its sequence value. A reset or marked replay already classified above keeps that earlier result.
6. For remaining fresh supported messages in other states: lower-than-expected tag 34 is INVALID/SEQUENCE_TOO_LOW; higher-than-expected is OUT_OF_SCOPE/RECOVERY_REQUIRED. Exact equality proceeds to the state table.
7. Check state eligibility first, then pending-request ownership, then TestReqID reuse. Apply the transition and increment the direction only on acceptance. Stop at the first terminal classification; do not evaluate later events except prevalidated corpus integrity. Out-of-range wire 34 is FRAME_INVALID at step 2; the bounded case cannot approach counter overflow from its initial value of 1.

The checker reports required recovery and unsupported cases rather than claiming a FIX engine should skip them. Reconnect must preserve real session continuity in a later design; starting a new offline case is not permission to reset a runtime session. Duplicate/replayed application data can never produce an SDK handoff in 3C0.

Classification is exactly IN_SCOPE_CONFORMANT, INVALID, OUT_OF_SCOPE or INCOMPLETE. Expected classification/code pairings are strict: COMPLETE belongs only to IN_SCOPE_CONFORMANT; EMPTY_SESSION, LOGON_REPLY_MISSING, TEST_RESPONSE_MISSING, LOGOUT_MISSING, LOGOUT_REPLY_MISSING and CONNECTION_LOST belong only to INCOMPLETE; PROFILE_OPTION_UNSUPPORTED, RESET_UNSUPPORTED, RESEND_UNSUPPORTED, SESSION_REJECT_UNSUPPORTED, MESSAGE_UNSUPPORTED, REPLAY_UNSUPPORTED, RECOVERY_REQUIRED, ERROR_LOGOUT_UNSUPPORTED and RECONNECT_UNSUPPORTED belong only to OUT_OF_SCOPE; all other named case codes in this contract belong only to INVALID. An unknown code or mismatched pairing is a corpus-schema error (exit 2). Each code listed in sections 17.3-17.5 has one named expected case or parameterized negative control. INVALID means violation of this selected contract; it is not a blanket claim that the behavior is forbidden in all FIX profiles.
